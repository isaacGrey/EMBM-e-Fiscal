# EMBM eFiscal development instructions

Implement the approved stack as a modular monolith. Follow [MASTER_SPEC.md](MASTER_SPEC.md) for financial, subscription, tenant, and regulator invariants. Keep identifiers, service credentials, and customer records out of source control and sample data. Use local infrastructure and synthetic data for development.

Present and develop EMBM eFiscal as a dedicated Philippine electronic invoicing platform by EMBM Services OPC. Invoice issuance comes first. Accounting integration, field mapping, invoice reconciliation, Save & Send Credits, and authorized reporting support that workflow. Preserve Sales Invoices, Credit Memos, and Sales Orders. Treat Sales Orders as supporting commercial documents with a final Save action and zero credit use. Keep Sales Orders out of electronic invoice delivery and BIR reporting. Follow the product boundaries in MASTER_SPEC.md when naming features, writing copy, and evaluating module scope. Keep the tagline “Invoice. Integrate. Comply.” and make claims about BIR accreditation, certification, or connectivity only with official verification.

Protect privileged functionality server-side. Enforce tenant isolation and permissions at the API and persistence boundary before introducing financial records. Enforce server-derived actions in the Documents module. Sales Invoices and Credit Memos use CommitAndSend with an idempotent, atomic commitment and credit deduction. Sales Orders use CommitOnly with no credit balance check or deduction. Commit eligible outbox work atomically and track its delivery and reporting results independently. Administrative roles cannot bypass document immutability. Keep live BIR transmission disabled and uphold read-only grant scoping.

Treat sender and template settings as versioned company administration. Authorize every configuration, document, PDF, attachment, email and source-order operation by subscriber and company. Never expose provider secrets or allow unverified sending or arbitrary SMTP network access. Keep issued files and pinned configuration versions immutable. External Sales Order retrieval only populates an in-memory invoice form and consumes no credits. Only a new, successfully committed Save & Send consumes a document credit.

Keep the billing catalog and purchased terms in versioned PostgreSQL records. Treat a payment redirect as status display and fulfill from a verified payment event. Use one ledger and wallet per subscriber and serialize mutations under the subscriber row lock. Keep the development payment simulator and local vendor controls gated to Development. Keep checkout authority, document action selection, entitlement checks, and credit consumption on the server.

Follow the integration priorities and phase boundaries in [MASTER_SPEC.md](MASTER_SPEC.md). Require official provider evidence for editions, regions, capabilities and production authorization. Validate declarative imports and operations, keep secrets scoped and referenced, enforce approved destinations and capabilities, preserve connector versions, and use the authorized Windows bridge for local APIs. Use only reviewed, deployed custom adapters. Connector configuration, testing, retrieval, synchronization and retries consume zero Save & Send Credits.

Read [PROJECT_PROGRESS.md](PROJECT_PROGRESS.md) and the relevant files under [docs](docs) before changing established behavior. Use Graphify for cross-module questions once its code graph is available, alongside targeted source searches. Refresh the local graph with `graphify extract . --code-only` after structural changes. Verify browser behavior and the affected API contracts before marking a change complete.

The official checkout is D:\Projects\EMBM-eFiscal\EMBM-e-Fiscal. The central repository for committed code is https://github.com/isaacGrey/EMBM-e-Fiscal.git on main. Before implementation, fetch origin, verify the branch and preserve local changes. Update a clean checkout by fast-forward only. For verified milestones, review the diff and untracked files for credentials, confidential data and unrelated changes, then commit reviewed files and push normally. Honor branch protection and required review. Never force push or overwrite diverged history. Verify the remote commit and report the actual commit hash and push result. This workflow does not authorize deployment.

Use Graphify for cross-module navigation and RTK for supported routine commands when installed. Use concise chat updates. Use Context7 for framework references and Playwright with browser diagnostics for functional verification when available. Use existing shared UI components. Where integrations are unavailable, use existing local tooling. Keep complete output for failures, financial or regulatory validation, security review, migrations, and final Git review. Do not enable external compression proxies or additional model services.
